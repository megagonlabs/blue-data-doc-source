KEY FINDINGS
────────────────────────────────────────────────────────────────────────────────

1. CHUNKER SPEED
   WindowChunker is the fastest (~24M wps) because it is a pure word-split
   sliding window with no regex overhead. SectionChunker is ~40% slower on
   structured text due to per-line header detection; it matches WindowChunker
   speed on unstructured text (no headers found, same code path). SentenceChunker
   is 4–5x slower than WindowChunker — sentence tokenisation (regex split or
   nltk) is the bottleneck.

2. SECTION COVERAGE
   SectionChunker is the only chunker that propagates section_title to
   ChunkRecord. On structured and mixed corpora it achieves 100% section
   coverage. On unstructured text it falls back to window chunking and produces
   identical results to WindowChunker (0% section coverage is expected).

3. CHUNK SIZE CONSISTENCY
   WindowChunker produces near-zero Std(wds) — chunks are exactly chunk_size
   words except the final one. SentenceChunker has low std (~4–7 wds) because
   sentences are short and uniform in this corpus. SectionChunker has high std
   (47–67 wds) because it respects section boundaries that vary in length;
   this is the intended behaviour.

4. PIPELINE STAGE BREAKDOWN — PRIMARY FINDING
   BasicEnricher (regex enrichment) consumes ~94% of total pipeline time at
   ~122 µs/chunk. Chunking costs only 7 µs/chunk. Embedding via
   DummyEmbeddingModel costs 1 µs/chunk (SHA-256 hash, no network).
   Implication: if enrichment output is not consumed downstream, disabling
   BasicEnricher is a ~10× end-to-end speedup. Real OpenAI embeddings will
   cost ~50–150 ms per API call, completely dominating the pipeline.

5. CHUNK SIZE SWEEP
   Smaller chunks (size=50) produce more chunks (282 vs 64 at size=500) and
   lower average words, but throughput drops ~20% because the SectionChunker
   header scan is called once per line regardless of chunk size. Above
   chunk_size=500 the corpus is too small to split further so chunk count
   plateaus at 64.
